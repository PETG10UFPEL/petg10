O buraco negro organizacional

Uma universidade cheia de dados
que não sabe por que decidiu

Um processo do SEI mostra o resultado. Não mostra o raciocínio. Esse é o nó que Bresque identifica empiricamente e que Gupta & Garg formalizam com precisão: «o raciocínio que conecta dado a ação nunca foi tratado como dado em primeiro lugar.»

📁
O que o SEI registra
Documentos, assinaturas, timestamps, status. O estado final de cada decisão. Exatamente como o Salesforce que Gupta & Garg criticam: sabe o preço final do contrato, não sabe quem aprovou o desconto e por quê — porque é «built on current state storage».

Novo · mecanismo do artigo completo
O loop que faz o Context Graph crescer — e por que isso importa
O CG não é uma foto — é um sistema vivo de retroalimentação

Cada decisão alimenta o grafo.
O grafo melhora a próxima decisão.

O ponto mais importante do artigo completo, ausente nas versões resumidas: o Context Graph não é um repositório estático de conhecimento. É um sistema de retroalimentação que cresce com cada decisão, tornando a próxima decisão mais informada — e eventualmente automatizável.

O loop de retroalimentação do Context Graph
Cada decisão alimenta o grafo · o grafo melhora a próxima · a autonomia aumenta gradualmente
Passo 1
Decisão humana
Gestor avalia contexto multi-sistema, aplica norma, concede exceção. O raciocínio existe — só na cabeça.
Passo 2
Captura do rastro
BPM instrumentado registra: inputs coletados, política avaliada, exceção invocada, aprovação, rationale — como dado estruturado.
Passo 3
Precedente consultável
Rastro vira precedente pesquisável. Próximo gestor consulta: «houve caso análogo?» — e obtém resposta com base real da UFPel.
Passo 4
Automação gradual
Casos repetidos: agente executa sem intervenção humana. Casos novos: vai ao humano — que gera novo rastro. O grafo nunca para.
↩ cada decisão automatizada também gera um rastro · o loop continua indefinidamente
Traduzindo para a UFPel: o SEI hoje é um sistema de estado atual — captura o resultado («DEFERIDO»). Um Context Graph sobre o SEI seria um sistema de raciocínio acumulado — captura a evolução das decisões e o porquê de cada uma. «O grafo se torna a fonte real de verdade para a autonomia — porque explica não apenas o que aconteceu, mas por que foi permitido acontecer.» — Gupta & Garg (2025)

Sistema apresenta casos análogos com norma, exceção e rationale aplicados

O que Bresque identificou sem nomear: a capacitação estratégica que ele recomenda como próxima etapa é precisamente o que habilita o loop. Gestores que sabem registrar o raciocínio, não apenas tramitar documentos, são o combustível do feedback loop. Sem isso, o grafo não cresce.

Novo · argumento estrutural do artigo completo
Por que o SEI sozinho nunca será um Context Graph
O argumento do write path vs. read path — devastador para incumbentes

Estar no write path decisório
é a condição incontornável

Gupta & Garg fazem uma distinção técnica que elimina os sistemas estabelecidos: capturar rastros exige estar no write path — no momento exato em que a decisão acontece. O SEI está no write path documental; não está no write path decisório. Essa diferença não pode ser remendada.

Write path decisório ✓
Quem vê o raciocínio no momento em que acontece
O workflow que orquestra a coleta de contexto, avalia a política, roteia a exceção e registra a aprovação — em tempo real, não depois. No contexto da UFPel: o BPM/BPMN da SGTIC é a camada mais próxima desse ponto — o único orchestration layer que vê o processo enquanto ele acontece.
Pode construir um Context Graph
Read path / ETL tardio ✗
Quem recebe o dado depois que a decisão foi tomada
Sistemas de BI, relatórios periódicos, data warehouses. «Quando o dado chega via ETL, o contexto da decisão já sumiu.» Na UFPel: o SEI registra o documento final; o COBALTO registra o estado acadêmico atual; o SIAFI registra a execução financeira. Todos chegam depois do raciocínio.
Não pode construir um Context Graph

«Capturar rastros de decisão exige estar no execution path no momento do commit — não boltar governance depois do fato. Incumbentes podem tornar a extração mais difícil, mas não conseguem se inserir em um orchestration layer do qual nunca fizeram parte.»

— Gupta & Garg (2025) · Foundation Capital · «Why incumbents can't build the context graph»

Diagnóstico estrutural: o SEI, tal como está, é arquitetado como o Salesforce que Gupta & Garg criticam — «knows what the opportunity looks like now, not what it looked like when the decision was made». Isso não é falha de implementação: é limitação arquitetural. O Context Graph não é um upgrade do SEI — é uma nova camada que precisa ser construída sobre o ecossistema existente, instrumentando o BPM como orchestration layer.

O que torna a UFPel diferente — e mais bem posicionada do que parece

No artigo de Gupta & Garg, a vantagem estrutural é de startups nativas de IA que «sit in the orchestration path desde o primeiro dia». Mas universidades públicas têm um ativo que startups não têm: 7 anos de decisões acumuladas. O SEI da UFPel tem 365 mil processos, 185 bases de GC e um BPM já operando. O grafo não começa do zero — precisa ser instrumentado sobre o que já existe. Essa é uma vantagem de tempo irreplicável.

⏱️
7 anos de precedentes latentes
365 mil processos que, com mineração e estruturação retroativa, podem alimentar o grafo com precedentes históricos. Uma startup começa do zero. A UFPel começa com um patrimônio decisório imenso — só não foi tratado como dado ainda.
🏗️
BPM como orchestration layer nativo
A SGTIC já opera o mapeamento BPM — que é exatamente o orchestration layer onde o CG deve ser instrumentado. A infraestrutura conceitual existe. Falta a instrumentação para capturar raciocínio, não apenas fluxo.
📚
185 bases de GC como layer de regras
O CG precisa de regras como ponto de partida. A UFPel já tem. As bases de GC são a layer de regras sobre a qual os rastros de decisão serão sobrepostos — exatamente a distinção regra/rastro que Gupta & Garg formalizam.

Agenda prática
Roadmap: do SEI ao Context Graph em cinco movimentos
Diretrizes de Bresque (2026) + lógica do feedback loop de Gupta & Garg · a ordem importa

Cinco movimentos —
na ordem que o loop exige

As recomendações de Bresque já apontam o caminho. O artigo de Gupta & Garg mostra por que a ordem importa: o loop só começa quando o write path decisório está instrumentado. Sem isso, os demais movimentos produzem mais documentos — não um grafo.

Movimento 1 · Já em curso — fundação
Consolidar a trazabilidade documental e expandir as bases de GC
Write path documental funcionando. 185 bases de GC como layer de regras. BPM da SGTIC operando. Esse é o alicerce — e precisa ser expandido para todas as 545 unidades antes de qualquer passo seguinte. Sem a layer de regras completa, o CG não tem onde se apoiar.
Movimento 2 · Passo crítico — inicia o loop
Instrumentar o BPM para capturar rastros de decisão (ativar o write path decisório)
Implementar, nos processos mapeados pela SGTIC, campos estruturados de captura: norma aplicada, precedente consultado, exceção invocada, síntese multi-sistema, quem aprovou e por quê. Este é o passo que inicia o feedback loop. BPM não é apenas otimização: é o orchestration layer onde o raciocínio é capturado como dado.
Movimento 3 · Gargalo tecnológico de Bresque
Resolver a interoperabilidade automática (viabilizar a síntese multi-sistema como dado)
A síntese COBALTO + SIAFI + SEI hoje é feita manualmente por E4. Para o CG capturar esse raciocínio, as APIs precisam permitir coleta de contexto multi-sistema em tempo real, no momento da decisão — não após o fato via ETL. Iniciativa SIPPAG como ponto de partida.
Movimento 4 · O gargalo humano — Bresque + Gupta & Garg
Capacitação em uso analítico-estratégico (ensinar gestores a registrar raciocínio)
O gargalo identificado independentemente pelos dois trabalhos: gestores foram treinados para usar o SEI, não para registrar raciocínio. O loop só retroalimenta se o gestor sabe que o rationale precisa ser explicitado. A próxima geração de capacitação deve ensinar a diferença entre regra e rastro de decisão — e por que registrar o segundo é governança, não burocracia.
Movimento 5 · Horizonte — quando o grafo tiver massa crítica
Ativar agentes de IA sobre o Context Graph (SAD Ecosistêmico pleno)
Com rastros registrados e sistemas interoperáveis, agentes recomendam decisões com base em precedentes reais da UFPel. Começa com human-in-the-loop: o agente propõe, o humano valida, o rastro cresce. Com o tempo, casos rotineiros são automatizados; exceções novas vão ao humano e alimentam o grafo. Exatamente a agenda futura que Bresque indica — agora com o mecanismo de implementação claro.

O artigo integral de Gupta & Garg não muda a tese — torna-a mais precisa. Três contribuições que o resumo não capturava e que mudam como se implementa o Context Graph na UFPel.

⚖️
Regras vs. rastros: a distinção operacional
As 185 bases de GC são a layer de regras — necessária, mas insuficiente. O CG começa onde as regras terminam: captura como cada regra foi aplicada naquele contexto específico. A UFPel tem a layer de regras. Falta construir a layer de rastros sobre ela.
🔄
O loop que faz o grafo crescer
O CG não é uma foto — é um sistema vivo. Cada decisão registrada vira precedente; casos repetidos se automatizam; exceções novas vão ao humano e alimentam o grafo. O loop não para. Isso transforma o SEI de arquivo em memória institucional que se retroalimenta.
✍️
Write path: a condição incontornável
O SEI não está no write path decisório — está no write path documental. O BPM da SGTIC é o orchestration layer. Instrumentá-lo para capturar rastros é o passo que nenhuma melhoria incremental no SEI pode substituir. É uma nova camada, não um upgrade.

O que Bresque chama de SAD Ecosistêmico e o que Gupta & Garg chamam de Context Graph são a mesma arquitetura: um sistema que não apenas armazena o que a instituição fez, mas preserva e torna consultável o raciocínio com que ela governou — e usa esse raciocínio acumulado para tomar a próxima decisão de forma mais informada, isônoma e eventualmente autônoma.

— Síntese integradora · Context Graph aplicado à gestão universitária · maio/2026
Para os gestores da UFPel: cada «DEFERIDO» sem rationale é um precedente perdido e um ciclo do feedback loop que não aconteceu. O Context Graph não é uma nova tecnologia — é uma nova prática de governança. E começa na próxima decisão que alguém registrar por que tomou, e não apenas o que decidiu.
